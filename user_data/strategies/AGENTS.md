# Strategies Agent Rules

- General Hyperopt rules now live at `C:\FreqTradeStuff\ai_guidance_docs\02_rules\rules_hyperopt_general.md`.
- Current 3KI exit/risk research rules now live at `C:\FreqTradeStuff\ai_guidance_docs\02_rules\rules_exit_and_risk_research.md`.
- Do not create 3KI exit/risk research strategy files in this folder unless the user explicitly approves it. Use the routed research strategy path from `C:\FreqTradeStuff\ai_guidance_docs\00_project_control\objective_current.md`.
- Strategy files intended for HyperOpt must be standalone strategy modules, including current and future sieve files.
- Do not use parent strategies, mixin strategy bases, or external strategy helper files for hyperopted strategy files. Freqtrade multi-process HyperOpt pickling can break when strategy logic depends on helper files or inherited strategy classes.
- Indicator modules under `user_data/Indicators/` are allowed dependencies when the task explicitly uses indicator outputs; do not edit indicators unless the user asks.
- Strategy agents cannot tweak, retune, or reshape indicators. Indicator contracts take priority; adapt strategy files to the current strategy-facing indicator outputs.
- Strategy agents may suggest indicator improvements or ask for additional strategy-facing levers, but they must not implement those changes inside indicator files.
- Strategy-agent work is limited to strategy files and explicitly requested strategy infrastructure. The objective is to find statistically qualitative entries through Sieve diagnostics, not to make indicators fit a strategy idea.
- Current active Sieve work is Sieve3 exit development. Active Sieve3 strategy files live directly in this top-level `user_data/strategies` folder as `sieve3*.py` files, not in `sieve3/` or `sieve3_candidates/` subfolders.
- During the Sieve3 exit-development campaign, old Sieve1/Sieve2/generated/candidate material should be archived out of the active top-level strategy set unless the user explicitly asks to restore it. Keep only active `sieve3*.py` files and required shared support files such as `sieve_guard_helpers.py` at top level.
- Rejected Sieve3 files go to `Archive/` only when the user decides they are rejected. Passed Sieve3 files go to a new successful-strategy folder only when the user decides they passed. There are no fixed pass/fail thresholds for Sieve3 yet; pass/fail is at user discretion.
- Temporary Sieve3 backlog-clearing guidance: while clearing the current top-level Sieve3 exit backlog, files that produce fewer than `10` validation trades across multiple windows should be parked in `sieve3_low_trade_long_window_retest/` for later longer-window testing. This is not a permanent pass/fail rule and does not mark them rejected or passed.
- The general Sieve3 campaign goal is to Hyperopt all active top-level `sieve3*.py` files across multiple windows and multiple random seeds, then report results for user discretion.
- Active sieve generations are entry-testing only until the user explicitly finalises the entry sieves. Do not add, tune, or optimise exits, stoploss logic, take-profit logic beyond the configured sieve target tests, leverage, position sizing, DCA/adds, cooldowns, protections, or broader exit/risk behavior during Sieve2 entry refinement. This restriction does not apply to the current Sieve3 exit-development campaign.
- Entry-test Sieve files must let the launcher control fixed TP/SL through `entry_sieve_minimal_roi(...)` and `entry_sieve_stoploss(...)`, or an exact env-driven equivalent. Do not hardcode class-level ROI/stoploss in entry Sieve files.
- For exit-stage Sieve work, disable launcher exit control and let the strategy's exit branches own TP/SL, trailing, partial exits, stop movement, and target-provider logic.
- Sieve entry results have no pass/fail or acceptance criteria. Treat results as informative diagnostics for refining useful entry signals. Sieve3 exit pass/fail is also not rule-thresholded yet; the user decides which Sieve3 files are rejected, kept for more testing, or moved to the future successful-strategy folder.
- Current Sieve2 work may test promising Sieve1 entries with better guard structure, multi-timeframe context, and cleaner confluence.
- Sieve2 rescue work is still Sieve2. Weak-but-not-hopeless Sieve2 foundations should be cloned into updated top-level `sieve2_overtrade_*`, `sieve2_loosen_*`, or similarly explicit `sieve2_*` files. The original pre-update Sieve2 files should be parked in subfolders for later review so the top-level active set contains only the current runnable Sieve2 update batch.
- Overtrading Sieve2 entries are not automatically failures. If they show profit, near-profit, strong asymmetric behaviour, or a plausible structural edge, create guarded Sieve2 variants first. Typical rescue hypotheses are: higher-timeframe structure or volume-profile context says the trade direction has support, while the lower timeframe supplies the exact breakout, reclaim, retest, local BOS/CHOCH, or failed-break entry.
- Sparse but high-winrate Sieve2 entries are also not automatic failures. If the logic is sensible but trade count is too low, create loosened Sieve2 variants that broaden entry timing or nearby structural-level acceptance while preserving the original market idea.
- Higher timeframe evidence should be preferred as the confidence source when designing Sieve2 rescue variants. A 4h/1d/3d level, pattern, VP state, BOS/CHOCH state, or prior-level state should define the broader condition where possible; 1h/4h should execute only when price action gives a location-specific entry.
- Do not move a noisy or sparse Sieve2 foundation into Sieve3 simply because it is interesting. Sieve3 is reserved for cleaner performers and strong foundations after Sieve2 review. Rescue variants must prove themselves as Sieve2 first.
- High-winrate low-trade pattern ideas may be parked as complete-pattern candidates rather than forced into Sieve3 immediately. Keep them reviewable for later broadening or pattern-specific research.
- Strong Sieve2 performers should not be promoted straight to Sieve3 from a single balanced target run. When the user requests it, run a fixed target validation such as TP 4% / SL 2% first; treat that as entry-signal evidence only, not exit optimisation.
- Low-volume non-pattern Sieve2 entries need a repair hypothesis before promotion. Prefer loosening overly tight guards, adding alternate structural triggers, or broadening nearby level acceptance, then rerun as Sieve2.
- Moderate/high-volume Sieve2 entries around 40% to 55% win rate, profitable high-trade entries, and entries with strong profit relative to win rate/trade count should usually be tuned as Sieve2 instead of rejected.
- High-volume Sieve2 entries below roughly 40% win rate with weak expectancy should usually be parked in rejected unless the agent can explain a clear structural rescue path.
- Original Sieve2 files moved to `sieve2_originals_failed` are parked originals, not necessarily dead concepts. They may have updated top-level rescue clones. The parked file comment or manifest should explain whether it was parked for overtrading, sparse trading, weak expectancy, redundancy, or no clear repair path.
- Use the active sieve pass prefix and class prefix consistently, for example `sieve2_` files with `Sieve2` classes for the current Sieve2 pass.
- Sieve progression is generation-based, not idea-age-based. When the research workflow moves to Sieve3, both refined Sieve2 foundations and brand-new ideas should use the `sieve3_` file prefix and `Sieve3` class prefix.
- Sieve3 promotion should be guided by the trading idea and result shape, not by rigid thresholds. Review score, winrate, trade count, profit, drawdown, TP/SL behavior, and whether the entry logic has a real market structure explanation before deciding whether to keep, split, reframe, or archive a foundation.
- Sieve3 result-shape examples are guidance, not an exhaustive rulebook. High-winrate low-trade entries may deserve variants that loosen timing, broaden nearby structural levels, or add a cleaner lower-timeframe execution trigger. Profitable high-trade entries with sub-50% winrate may deserve precision variants such as retests, VP/TLV2 location guards, local BOS/CHOCH, failed-break filters, volume-pressure confirmation, or market-state guards. Strong 4/2 TP/SL behavior around 40%+ winrate may deserve preservation of the asymmetric target idea while refining entry quality. High-profit but high-drawdown ideas may deserve guard/refinement variants before any exit work is considered. Low-drawdown stable ideas and structurally sensible near-misses may deserve narrow repair-path variants. Other good options are allowed when the agent can explain the market-structure reason and keep the branch focused.
- Refined next-generation files must preserve traceability with explicit module-level metadata such as `SIEVE_STAGE`, `SOURCE_STRATEGY`, `SOURCE_RESULT_BATCH`, and `RESEARCH_PATH`.
- Brand-new ideas introduced during Sieve3 should use `sieve3_novel_*` filenames/classes and explicit metadata such as `NOVEL_IDEA = True`; do not send new ideas back to stale `sieve1_` naming just because the idea is new.
- One promising source strategy may split into multiple next-generation files when testing distinct refinement paths. Keep each branch narrow and name it by the refinement path, for example `_vp_guard`, `_tlv2_guard`, `_htf_context`, `_retest`, `_local_structure`, `_vp_tlv2_guard`, or `_retest_htf_guard`.
- Do not combine every possible improvement into one cloned strategy. Agents may apply multiple refinement options across multiple cloned files, but each cloned file must have a clear research hypothesis.
- Do not discard promising foundations because they do not match the current discussion focus. Promising foundations include high-winrate low-trade ideas, profitable high-trade low-winrate ideas, strong profit relative to trade count, strong `4/2` target behaviour with roughly 40%+ winrate, low-drawdown stable ideas, and structurally sensible near-misses with clear repair paths.
- Trade count is context, not a hard acceptance rule. Avoid promoting sub-20 trade results unless the user explicitly wants sparse probes, but do not throw away low-trade high-winrate or high-risk/reward ideas solely because they are not high volume.
- Unsuccessful strategies may be archived out of the active top-level strategy set when results and critical logic review show they are weak or structurally unhelpful. Before parking a file, add a short module-level comment explaining why it was archived, including the result pattern or logic flaw that drove the decision.
- Archived strategy comments should be reviewable later. Prefer concise reasons such as consistently negative across targets, excessive trade count with poor expectancy, generic/non-structural trigger, lookahead-risk concern, redundant duplicate, or no clear repair path.
- Sieve strategy names should describe the entry idea directly. Do not use vague generator-origin tokens such as `test` or `codex` in filenames, class names, or visible entry tags.
- Sieve strategies with multiple core entry ideas should use `multiN` filenames/classes, where `N` is the number of core entry concepts being tested for confluence.
- Broad `multiN` confluence probes may use hyperoptable batch selectors/enables to discover useful combinations. When results show a promising confluence scenario, flag it to the user as a candidate for extraction into a narrower dedicated strategy for refinement.
- Split sieve files by entry concept, not by every guard combination. Optional guards such as 4h/1d volume-profile context should be hyperoptable enable/disable parameters inside the entry-concept strategy.
- Do not use moving averages, EMA/SMA trend filters, MACD-style average crosses, RSI, Bollinger, stochastic, or generic TA-stack logic as Sieve entry guards.
- Preferred Sieve guards are active project indicator outputs, directional volume pressure, accumulation/distribution pressure, relative or rising volume, candle body direction, close-vs-previous-close direction, and simple reclaim/rejection/cross/follow-through behaviour around project-indicator levels.
- Daily TOP10 strategy files should normally be kept out of sieve runs by targeted sieve-prefix filtering because they contain broader strategy scaffolding, not just entry-condition refinement.
- Multi-timeframe sieve strategies must combine a higher-timeframe trading condition with lower-timeframe structural execution. A higher-timeframe context plus a generic candle/momentum trigger is not enough.
- MTF files must make the hierarchy explicit in the filename, class name, and entry tag: higher timeframe, higher-timeframe concept, lower timeframe, and lower-timeframe execution trigger.
- Prime higher-timeframe contexts include 1d/3d/4h patterns such as flags, pennants, head-and-shoulders, inverse head-and-shoulders, triangles, channels, rectangles, triple tops/bottoms, Wolfe-like structures, TLV2 levels, volume-profile VAH/VAL/POC/HVN/LVN acceptance or rejection, BOS/CHOCH, HH/HL/LH/LL structure, supply/demand, and prior high/low levels.
- Prime lower-timeframe execution triggers include 1h/4h breakout through the relevant level or pattern line, break-and-retest, rejection/reclaim, failed break, local BOS/CHOCH, and higher-low/lower-high continuation at the relevant level.
- Retests are first-class strategy variants, especially for TLV2 levels, volume-profile levels, and 1d/3d pattern lines. When possible, test raw breakout and retest variants separately.
- Volume pressure, rising volume, candle direction, and close-vs-previous-close behaviour may support a structural trigger, but must not be the primary lower-timeframe trigger in an MTF strategy.
- Avoid `momentum_confirm`, single-candle close direction, EMA/SMA pullback, or oscillator/average-cross logic as the primary trigger for MTF entries. These are only acceptable as optional secondary guards after a location-specific structural trigger.
- MTF strategies should usually reduce the entry set. If an MTF strategy produces thousands of trades or trades far more often than its single-timeframe parent, treat that as a design failure unless there is a clear trading reason.
- Do not create an MTF strategy when the higher-timeframe condition has no clear location, invalidation, or entry line that the lower timeframe can refine.
- Before editing sieve or strategy infrastructure, check that local definitions for "sieve", "strategy", "entry", "exit", "guard", "acceptance", and result interpretation are still accurate. Report deviations or stale instructions to the user instead of silently coding against outdated definitions.
- Root-cause first: before adding fallback/workaround code, identify and fix the underlying mapping/config/state issue.
- Do not add defensive or rescue code by default to "make it work".
- Prefer one-time data/state/path migrations over persistent runtime workaround logic.
- If a workaround seems unavoidable, stop and ask for explicit approval before adding it.
